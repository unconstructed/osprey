## 1. What's working

- **One decision function for both engines.** The Nautilus runner calls each reference rule's own decision function,
  so the two runners decide with the same code and parity tests the accounting alone. That is the owner's option B,
  already in practice.
- **Parity is tight and honest.** All 198 Nautilus contract cases pass, and parity holds to 1e-9 (about 1e-14 seen).
  The tolerance is written down with its reason. The one real difference (round-off legs are not sent) is documented,
  tested, and checked on real data against a bound. Bug #61 was triaged case by case, and nothing was loosened.
- **The real-data check paid off.** It found a case the synthetic tests cannot reach (section 2, item 2). It read only
  train closes, and its panels hash to the values the studies pinned.
- **Throughput was measured before any sweep was sized on it.**
- **The studies' luck controls keep working.** Three NO EDGE verdicts (dip-timing, rebalance-steady, trend-steady)
  were accepted as they stood: no reruns, and no validate look spent.
- **`risk-officer` listed the tests its five-level change would break** before touching `config/`.

## 2. Top improvements, ranked

### 1. A result and its luck controls must run on one engine (stops luck passing as skill)

**Problem.** The milestone report says the reference engine "stays the tool for the studies' exhaustive luck
controls; results that count run on Nautilus". A verdict compares S, the walk-forward result, against controls that
re-run the backtest: shifted schedules, placebos, random entries, plateau and grid steps. If S comes from one engine and
its controls from another, any systematic gap between the engines moves the comparison one way.
- Where parity exists, the gap is tiny. But the one documented difference always helps Nautilus: it skips round-off
  legs and their gas, and the reference pays for them.
- Every study so far ran its controls on `lab/runner/portfolio.py`. That engine has no Nautilus version and no parity
  test.
- Hard rule 3 says only Nautilus results go into reports, and nothing in AGENTS.md allows controls on the reference.

**Cost.** On daily bars Nautilus is affordable. The runner does about 60,000 full-history runs per hour per core.
trend-steady's whole run 0 took about 4 CPU-minutes on the reference, which is roughly 1-2 CPU-hours at 10-25x slower.
Multi-asset runs will be slower.

**Change (patch).**
- AGENTS.md "Running many simulations" gets a new rule 6. S and every control that re-runs a backtest run on
  NautilusTrader. Using the reference for a counted control is the owner's decision, and it would need a parity test
  plus S computed on both engines, agreeing within `TOL`. Bootstraps of S's own returns are not affected.
- `backtest-auditor` gets checklist item 18, "Provenance": the engine, the snapshot, the commit and seed, and the full
  tier on that commit, so the final step now reads "items 1–18".
- One matching rule each in `quant-researcher.md` and `research-methods.md`.

**Benefit.** No verdict can rest on a result and a null from two different engines.

**Risk.** More compute. The owner can allow the reference under parity (question 1).

### 2. Real-data parity and real-price shapes for every engine (stops wrong numbers)

**Problem.** Bug #61's moving-price round-off leg showed up only on real hourly data. I checked it on the train
bars:
- On the Kraken bar closing 2020-04-09 19:00 UTC, the 50/50 rebalance filled at an open of 7299.4. That is exactly the
  previous fill's open, 30 bars earlier. The reference traded a 3.3e-16 leg and paid 0.10 USD of gas for it.
- Real prices have few decimals, so they repeat exactly: about 1 hourly close in 3,500 equals the close 30 hours
  earlier.
- The contract suite's `random_bars` draws continuous prices, which never repeat. So the parity property cannot reach
  this case, and nothing pins it. Its comment says the draws "never reach it". TESTING.md rule 3 asks for a regression
  test.
- The real-data script covered Kraken BTC only. Binance (USDT prices with two decimals) and ETH were not checked.

**Change (patch).**
- AGENTS.md "Milestones" gets a short "Closing a milestone" list. An engine milestone runs against the reference on real
  train bars: Kraken and Binance, BTC and ETH, daily and hourly, costs at 1x and 2x. Every case found becomes a
  hand-built test.
- TESTING.md section 7 gets two new patterns: "Real prices are discrete" and "Real-data parity".

**For the engine owner (code, not in the patch):**
- a hand-built test of the exact-repeat case;
- a parity property that also draws prices rounded to 1-2 decimals and handles the documented difference as
  `scripts/nautilus_parity_real.py` does;
- an `--instrument` option on that script, then the Binance and ETH runs (about 16 more runs, a few minutes), before
  milestone 3 starts.

**Risk.** A few minutes per engine change.

**Risk.** A key to manage, and read-only network access widened by two hosts.

### 4. Get ready for milestone 3 (genuinely different strategies need a multi-asset engine)

**Problem.**
- The Nautilus runner is single-asset. Everything that needs to run is multi-asset: all three launch strategies, all
  four studies, and the app's hold-this-mix and Cash-first numbers (which `docs/app/technical.md` says must be Nautilus
  backtests). Milestone 3's "done when" did not mention the multi-asset runner.
- The decision function is captured by swapping `reference._simulate` for a moment, under a thread lock
  (`nautilus.decider`). That works for process pools. But it ties option B's "shared library" to one engine's internals,
  and the multi-asset engines use a different callback.
- `quant-researcher.md` step 3 says to write a Nautilus `Strategy`, which conflicts with option B.
- No role owns `lab/runner/`, `lab/costs/` or `lab/tracking/`. Milestone 2's work had no role file, and milestone 3's
  runner has no owner.

**Change (patch).**
- AGENTS.md "What's left to build" gains the multi-asset runner and option B's decision function with a
  decision-parity test, and milestone 3's row names the runner and its parity test.
- `quant-researcher.md` step 3 is rewritten the same way.
- A new role file, `.claude/agents/lab-engineer.md`, owns the engines, the contract and parity tests, throughput and
  real-data checks, and gets one row in "Desk roles".

**Recommended (code).** Expose each rule's decision function as a public, engine-free function before the strategies
are written, instead of capturing it.

**Risk.** One more role file to keep current. The owner may prefer to give the engines to `quant-researcher`
(question 3).

## 3. Out-of-date instructions fixed in the patch

**From your list (each one verified):**
- **`BacktestNode`.** AGENTS.md (rule 1 and "What's left to build"), research-methods.md and HOWTO.md now say what was
  built: one `BacktestEngine` per run, disposed after use. The node builds the same engine from a config, and the owner
  can ask for it (question 6).
- **The contract row and the `on_bar` example.** AGENTS.md and HOWTO.md now give the columns `ret`, `position`,
  `turnover` and `cost`, the attrs `trade_returns` and `n_trades`, and fills at the next open. The example multiplies
  the per-bar forecast by `sqrt(bars_per_year)`. TESTING.md 4a.8 marks both as fixed.
- **`uv run mlflow ui`.** This is worse than not showing our runs. I checked `mlflow ui --help` and MLflow 3.18's
  `_get_default_tracking_uri`:
  - Without `--backend-store-uri`, it opens `sqlite:///mlflow.db` in the current folder. (Our `mlruns/` holds a SQLite
    file, not a file store, so the `./mlruns` fallback doesn't apply.)
  - Run from the repo root, it shows an empty store and creates an untracked `mlflow.db` there.
  - The studies' dirty-tree guards count untracked files (#52), so that file would block every real run.

  The fix is `uv run mlflow ui --backend-store-uri sqlite:///mlruns/mlflow.db`, plus `/mlflow.db` in `.gitignore` and in
  AGENTS.md's copy of it. `lab/tracking/mlflow_log.py`'s docstring has the same wrong command; that is code, so it's
  for the engine owner.
- **Three risk levels.** AGENTS.md, `quant-researcher.md` and `risk-officer.md` now say five levels, and that the file
  still holds three until `risk-officer` writes the other two. AGENTS.md's YAML copy also lacked Steady's 35% budget
  and the `hold_mix` key.
- **README.md and `dashboard/status.json`.**
  - The README "Status" block, its file table and its "not in this repo" list were all wrong; research-methods.md and
    the app docs are here.
  - `status.json`: milestone 2 is `done`, with a note that it counts once the full tier passes on `6d78801`. Open work
    5.1-5.3, 5.6 and 5.7 are `done`; 5.4 and 5.5 are `in_progress`. I set 5.4 from the risk-officer's note that mutation
